# Research — Linux kernel: USB, binding, modules and firmware

- **Sources:** kernel source collected in `/tmp/ksrc` (file:line cited),
  local host `modules.alias` (6.17.0-oracle), upstream documentation.
- **Rule:** fact without citation = UNKNOWN.

## 1. sysfs — where each thing lives (CONFIRMED, verified on host + source)

**Device** node (`/sys/bus/usb/devices/1-2`):
`idVendor`, `idProduct`, `bcdDevice`, `bDeviceClass/SubClass/Protocol`,
`manufacturer/product/serial` strings, `uevent`. **No `modalias`** (verified
on host; the attribute does not exist on the device node).

**Interface** node (`1-2:1.0`): `modalias`, `bInterfaceClass`,
`driver` symlink. Source: `modalias_show` in `/tmp/ksrc/sysfs.c:1157`
emits from `intf->cur_altsetting` — only exists for interfaces:

```c
return sysfs_emit(buf,
        "usb:v%04Xp%04Xd%04Xdc%02Xdsc%02Xdp%02X"
        "ic%02Xisc%02Xip%02X", ...);
```

Root devices are `usbN`; nodes with `:` in the name are interfaces.

## 2. modules.alias — modalias → module matching

Generated by kbuild (`file2alias.c`) from drivers' `usb_device_id` tables.
Line format:

```text
alias usb:v0BDAp8811d*dc*dsc*dp*icFFiscFFip00in* rtl8xxxu
```

`d*` means "any bcdDevice"; drivers pinning a revision emit
`d0200*` etc. Kernel resolution (modprobe) matches the interface modalias
against these expressions; the tool replicates the same glob algorithm over
the file, in file order, and records which line matched as evidence.

## 3. new_id — dynamic bind, the exact mechanism

`usb_store_new_id` (`/tmp/ksrc/driver.c:42-67`), CONFIRMED:

```c
fields = sscanf(buf, "%x %x %x %x %x", &idVendor, &idProduct,
                &bInterfaceClass, &refVendor, &refProduct);
if (fields < 2)
    return -EINVAL;
...
dynid->id.match_flags = USB_DEVICE_ID_MATCH_DEVICE;
```

- Accepted format: `VID PID` (minimum 2 hex fields); optional field 3 =
  `bInterfaceClass` (refines the match); fields 4-5 = refVendor/refProduct.
- After insertion, the driver re-probes existing devices.
- **Limitations:** does not survive reboot; requires the module already loaded;
  and some drivers disable the mechanism — critical case:
  `rtl8xxxu` has `.no_dynamic_id = 1` (see docs/research/realtek.md §1).
- Read-back: `new_id_show` lists the inserted dynids
  (`driver.c:114-130`) — the tool can verify its own bind.

## 4. Bind persistence

Since `new_id` is volatile, legitimate post-reboot persistence via one of:

1. **modprobe.d alias** — create a `.conf` in `/etc/modprobe.d/` with an alias
   whose value matches the device modalias pointing at the module
   (e.g.: `alias usb:v0BDApF000d*dc*dsc*dp*icFFiscFFip00in* rtl8xxxu`);
   systemd/udev coldplug runs `modprobe` by alias at boot.
2. **udev rule** with `DRIVER==`/explicit bind via helper script — more fragile
   (depends on ordering and an external binary).

V1 choice: modprobe.d alias (declarative, reversible by removing the file,
no code execution). Declared risk: custom aliases survive kernel upgrades
because the modalias does not change with the kernel.

## 5. Blacklist and blocking (State D)

Syntax: `blacklist <module>` prevents automatic alias resolution;
`blacklist <module>` in `/etc/modprobe.d/*.conf`; precedence: last file
in lexicographic order wins on option conflict; `install <mod> /bin/false`
blocks entirely.

### Secure Boot — confirmed messages in dmesg

When Secure Boot is active and an unsigned module is loaded, the kernel
emits **one or more** of the following lines (sources: `security/lockdown/lockdown.c`,
`kernel/module/signing.c`, `kernel/module/main.c`; strings unchanged between
5.15 and 6.17):

1. **Lockdown lock-out** (`CONFIG_LOCK_DOWN_IN_EFI_SECURE_BOOT=y` — default
   on Ubuntu/Debian; absent in vanilla upstream):
   ```
   Lockdown: <comm>: unsigned module loading is restricted; see man kernel_lockdown.7
   ```
    - File: `security/lockdown/lockdown.c:66-68`
    - v5.15 uses `pr_notice`; v6.1+ uses `pr_notice_ratelimited`.
    - `lockdown_reasons[]` texts in `security/security.c:62`:
      `[LOCKDOWN_MODULE_SIGNATURE] = "unsigned module loading"`.

2. **Explicit rejection** (`CONFIG_MODULE_SIG_FORCE=y` or `module.sig_enforce=1`):
   ```
   Loading of unsigned module is rejected
   ```
    (or `Loading of module with unavailable key is rejected`,
    `Loading of module with unsupported crypto is rejected`).
    - File: `kernel/module/signing.c:120`.

3. **Kernel taint** (sig_enforce=0, module loaded anyway):
   ```
   <modname>: module verification failed: signature and/or required key missing - tainting kernel
   ```
    - File: `kernel/module/main.c` (line varies: 2747 on v6.1, 2046 on v6.6,
      2064 on v6.12, 2547 on v6.17). Uses `pr_notice_once`.

Indicators that Secure Boot is active at boot:

- **vanilla upstream**: `Secure boot enabled` (`arch/x86/kernel/setup.c:1163` on v6.17)
- **Ubuntu/Debian** (local pr_fmt): `secureboot: Secure boot enabled`
- **SB-triggered lockdown**: `Kernel is locked down from EFI Secure Boot mode; see man kernel_lockdown.7`

Fixture updated in `tests/fixtures/__init__.py:DMESG_SECURE_BOOT_REJECTION`.

## 6. Local verification (host)

Host with three Oracle 6.17 kernels installed. The **running** one (uname -r =
6.17.0-1018-oracle) packages no wireless/BT modules. Installed
6.17.0-**1020**-oracle ships **194 wireless modules** (verified via find),
including mt7601u with real aliases (`modinfo` against that tree worked).

Product implications:

1. The tool must resolve `modules.alias` for the **running** kernel
   (`uname -r`), never "the newest installed" — and explicitly detect the
   "new kernel installed, reboot pending" scenario, where driver/firmware already
   exist in the future tree but not in the active one.
2. Test fixtures derive from the sources cited here, not from the host.
3. "Kernel with no drivers at all" remains a valid State E scenario.
